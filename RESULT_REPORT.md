# Win probability → rviewer: integration report

How to add the **map and series result model** of this repo to rviewer's **Veto Predictor**
page. Once the two teams are chosen (and, optionally, some veto steps are locked), the page shows
the probability that each team wins the series, the 2-0 / 2-1 / 1-2 / 0-2 distribution, and per
map the win probability and the most likely score. Built on 2026-10-01; snapshot dated
2026-09-28. The veto side is unchanged (`REPORT.md`).

## 1. What exists and what is verified

| Piece | Here | In rviewer (proposed) | Status |
|---|---|---|---|
| Model + snapshot | `map_result_glm.ipynb` section 10 → `export/result_*.csv` | Supabase tables `result_*` | Generated by the notebook (~40 s) |
| Dependency-free TS engine | `rviewer_port/resultPredict.ts` | `lib/resultPredict.ts` | New |
| TS ↔ Python parity test | `rviewer_port/result_parity.test.ts` + `export/result_reference.json` | `scripts/result-parity.test.ts` + `data/` | **PARITY OK**, max \|Δ\| ≈ 3e-16 |
| UI | — | a panel in `components/sections/VetoPredictorSection.tsx` | To build (section 5) |

**How it works.** A binomial GLM estimates p = P(team A wins a round) from round counts. The
final score then follows exactly from Valorant's rules (first to 13, overtime won by 2), with a
map-level random effect (`sigma` = 0.4) because rounds are not independent. Without it, the model
predicts 15% overtime against ~11% real. Team strength is built from **players**: the mean
strength of the 5 players in the team's current lineup, plus the lineup's mean vlr rating. A
transfer therefore carries the player's strength to the new team. Three map probabilities (A's
pick, B's pick, decider) give the series, averaged over the exact veto distribution that
`vetoPredict.ts` already computes.

**Two models in the same snapshot** (the `model` column):

| `model` | What it is | P(win) depends on the veto? | When to use |
|---|---|---|---|
| `base` (default) | Player strength + lineup rating, the CV-chosen model | **No**: the same on every map | Default. The best-measured model |
| `map` | `base` + a strength per (team, map) | Yes | Optional toggle ("map-aware") |

With `base`, locking veto steps does **not** change the win probability. That is the model's
finding, not a bug: map-specific strength did not help in validation. The UI should say so (see
section 5).

**What the parity test covers.** Four pairs, including an unknown team, under both models. For
every map of the pool it compares the round-win probability, the map-win probability, the full
score distribution (104 scores) and the series outcomes over a 4-triplet veto distribution, all
with tolerance 1e-9 (actual ≤ 3e-16). It also checks the following:
- the score model sums to 1, is symmetric, and gives 50% at p = 0.5;
- swapping A and B gives the complement;
- an unknown team equals `__prior__`;
- `base` does not depend on the map;
- triplets collapsed from `vetoPredict`'s 5040 sequences sum to 1 (210 triplets), and a fully
  locked veto collapses to one triplet;
- the test metrics are present, and bad input throws.

## 2. How good it is: be honest in the UI

Walk-forward test on 670 maps / 272 BO3 series since 2026-07-01, never seen during model
selection. Log loss (lower is better; coin flip = 0.693):

| | Map log loss | Map accuracy | Series log loss | Series accuracy |
|---|---|---|---|---|
| `base` | 0.689 | 55.2% | 0.684 | 57.4% |
| `map` | 0.691 | 55.7% | 0.685 | 56.6% |
| Elo (reference) | 0.690 | 52.7% | 0.688 | 53.7% |
| Coin flip | 0.693 | — | 0.693 | — |

In validation (Jan–Jun) the model clearly beat Elo (0.668 vs 0.683). On Jul–Sep **no model,
Elo included, is meaningfully better than a coin flip**. The differences have bootstrap CIs that
include 0. So:
- present it as **experimental** ("Testing" section, like the veto predictor);
- show the probabilities as they are, never as a "pick";
- the snapshot's `result_meta` carries these numbers (`snap.testMetrics`), so the UI can show
  them without hardcoding.

## 3. Snapshot schema (Supabase)

```sql
create table result_team (
  model text not null, team text not null,
  strength float8,            -- round-logit strength of the current lineup; only differences matter
  lineup text,                -- 'p1|p2|p3|p4|p5' (most recent lineup), '' for __prior__
  lineup_rating float8,       -- mean smoothed vlr rating of that lineup
  n_maps int,                 -- BO3 maps of that team in the data (0 = prior)
  primary key (model, team)
);
create table result_team_map (
  model text not null, team text not null, map text not null,
  coef float8,                -- (team, map) effect; only for model = 'map'
  primary key (model, team, map)
);
create table result_meta (key text primary key, value text);

drop policy if exists "anon read" on result_team;
drop policy if exists "anon read" on result_team_map;
drop policy if exists "anon read" on result_meta;
create policy "anon read" on result_team     for select to anon using (true);
create policy "anon read" on result_team_map for select to anon using (true);
create policy "anon read" on result_meta     for select to anon using (true);
```

**Without the policies, reads return 0 rows and no error** (same trap as the veto tables). The
symptom is `result snapshot is missing the __prior__ row of model 'base'`. Sizes: 130 / 625 /
26 rows. `float8` keeps the CSV doubles exact, so parity holds after uploading.

`result_meta` keys: `snapshot_date`, `default_model`, `sigma`, `base_blocks`, `map_blocks`,
`{base,map}_lambda`, `{base,map}_half_life`, `test_since`, `n_maps_test`, `n_series_test`,
`{base,map,elo}_{map_log_loss,map_acc,series_log_loss,series_acc}` and
`coin_{map,series}_log_loss`.

In `scripts/upload.mjs`, add the three `result_*` tables the same way as the four `veto_*`
ones. Re-exporting replaces: truncate them before uploading
(`truncate result_team, result_team_map, result_meta;`).

## 4. Engine API (`lib/resultPredict.ts`)

```ts
import { enumerateSequences } from '@/lib/vetoPredict';
import { buildResultSnapshot, seriesPrediction, tripletsFromSequences } from '@/lib/resultPredict';

const rs = buildResultSnapshot(teamRows, teamMapRows, metaRows);              // result_* rows
const seqs = enumerateSequences(vetoSnap, teamA, teamB, pool, locked);         // already computed by the page
const pred = seriesPrediction(rs, model, teamA, teamB, tripletsFromSequences(seqs));
```

- `seriesPrediction(...)` → `{ pWin, outcomes: {'2-0','2-1','1-2','0-2'}, maps: Map<map, MapPrediction>,
  teamA, teamB, known: {a, b} }`. Everything is from **team A's side** (A = team that starts the
  veto, same as `vetoPredict`). Team B wins with `1 − pWin`.
- `MapPrediction` = `{ map, pRound, pWin, pOvertime, mostLikelyScore: [a, b], expectedRoundDiff, scores }`.
- `mapPrediction(rs, model, a, b, map)` for a single map. `roundWinProb(...)` is the bare
  round probability.
- `tripletsFromSequences(seqs)` collapses vetos to (A's pick, B's pick, decider) with their
  probability. A fully locked veto gives one triplet with p = 1.
- `teamInfo(rs, model, team)` → `{ strength, lineup, lineupRating, nMaps }`.
  `knownResultTeam(rs, team)` is false when the team falls back to `__prior__`.
- `rs.testMetrics`, `rs.snapshotDate`, `rs.defaultModel`, `rs.sigma`.
- Throws on an empty triplet list or probabilities that do not sum to 1.

Cost: 7 maps × 21 quadrature nodes × 104 scores per team pair, **< 1 ms**. Recompute on every
change of teams, locks or model. `enumerateSequences` (8–20 ms) is already the expensive part.

## 5. UI on the Veto Predictor page

A **"Win probability"** panel under the veto heatmap, driven by the same state (team A, team B,
pool, locked steps):

1. **Header bar:** `pWin` vs `1 − pWin` as a split bar with both team logos and percentages.
2. **Series outcomes:** four bars, 2-0 / 2-1 / 1-2 / 0-2 (from A's side, labelled with team
   names).
3. **Per map** (the maps of the most likely veto, or the locked picks/decider once known): map
   name, P(A wins the map) and the most likely score (for example, "13-10"). For the `base`
   model, show the per-map row **once** ("any map"), since it is identical for all maps.
4. **Lineups** under each team: `teamInfo(...).lineup` with the note "lineup as of
   {snapshotDate}". If `known.a` / `known.b` is false, say that the team has no data and the
   average was used.
5. **Toggle** "Map-aware model (experimental)" switches `model` between `'base'` (default,
   `rs.defaultModel`) and `'map'`. With `base`, show the note *"The veto does not change this
   probability: map-specific strength did not improve predictions."*
6. **Footer:** test metrics from `rs.testMetrics` for the selected model next to Elo and the coin
   flip, in one line, for example *"Tested on 670 maps since 2026-07-01: log loss 0.689 (Elo
   0.690, coin 0.693)"*.

The veto heatmap and locks need no changes. The panel only reads the `seqs` the page already
enumerates. `vetoDistribution` only returns the top-N sequences, so call `enumerateSequences` with the
same arguments to get all of them. That costs one more enumeration (8–20 ms), or the page can
call `enumerateSequences` once and pass its result to both.

## 7. Updating the model

1. **This repo:** run `map_veto_lightgbm.ipynb` (writes `export/veto_*` and
   `veto_played_test.csv`), then `map_result_glm.ipynb` (writes `export/result_*`). The result
   notebook needs the veto export, so keep this order.
2. **This repo:** `node --experimental-strip-types rviewer_port/parity.test.ts` and
   `node --experimental-strip-types rviewer_port/result_parity.test.ts` → both `PARITY OK`.
3. **rviewer:** copy the files of section 6, truncate the `veto_*` and `result_*` tables, run
   `node scripts/upload.mjs`, then run both parity tests over `data/`.
4. **If `resultPredict.ts` changed:** copy it again (and the test). If the model changes in
   Python without the TS, step 2 fails.

## 8. Limits

- **BO3 only**, like the veto model.
- **Frozen snapshot**, with lineups as of `snapshot_date`. A roster move after that date is not
  known: the team keeps its last lineup's strength. Re-export when new matches are loaded.
- **Current lineup only.** The engine does not take a custom lineup. Strengths are precomputed
  per team, and supporting arbitrary lineups would need player effects and ratings in the
  snapshot.
- **Unknown teams** use `__prior__`: no team or player effect, and the lineup rating of five
  unseen players.
- Maps of a series are treated as independent given the strengths. Form on the day is not
  modelled.
