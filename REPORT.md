# Veto Predictor → rviewer: integration report

How the veto model built in this repo runs inside
[rviewer](https://github.com/RkTcaster/rviewer) (Next.js + Supabase, no Python), what is
verified, and how to update it. Integrated in rviewer on 2026-09-17 (see
`../PREDICTION_MODEL_VETO.md` for the exchange between both repos).

## 1. What exists and what is verified

| Piece | Here | In rviewer | Status |
|---|---|---|---|
| Model snapshot | `map_veto_lightgbm.ipynb` section 9 → `export/*.csv` | Supabase tables `veto_*` | Generated by the full notebook run |
| Dependency-free TS engine | `rviewer_port/vetoPredict.ts` | `lib/vetoPredict.ts` | `tsc --strict` clean, also with rviewer's `tsconfig` options |
| TS ↔ Python parity test | `rviewer_port/parity.test.ts` + `export/veto_reference.json` | `scripts/veto-parity.test.ts` + `data/` | **9/9 cases OK**, max \|Δ\| ≈ 5e-16 |
| UI | — | `components/sections/VetoPredictorSection.tsx` (Sidebar → Testing) | Built in rviewer |

**How it works.** The model is the per-turn conditional logit (105 coefficients: pick,
first ban, second ban). At each step only the features that vary across candidate maps
matter, and all of them come from per team × map stats, global per-map stats, or ranks
within the available maps. That keeps the snapshot small and lets the TS engine rebuild
everything without Python. The engine enumerates the 5040 possible vetos with their exact
probability (120 distinct states) in **8–20 ms**, and can condition on steps that already
happened (live veto).

**What the parity test covers** (cases computed by the notebook and recomputed in TS):
4 pairs with a lot of history, one pair with few series, an unknown team (uses `__prior__`),
a pool different from the default, 2 locked steps and 5 locked steps. For each case it
compares **every** sequence probability and **every** per-step probability (tolerance 1e-9;
the actual difference is rounding, ~1e-16). It also checks that marginals sum to 1 by row and
column, that sequences respect locked steps, that the test metrics and `SLOT_ACTOR` are
exported, and that the engine rejects 6-map pools, locked maps outside the pool and maps
missing from the snapshot.

## 2. How good it is

Measured on the test period (272 BO3 series since 2026-07-01, never seen by the evaluated
model). These values travel in `veto_meta` and are read by the UI through `snap.testMetrics`:

| Metric | Model | Chance |
|---|---|---|
| Top-1 per step (given the real veto state) | 51.9% | 26.5% |
| Played maps (picks + decider), most likely veto | 57.2% | 42.9% |
| Decider right, most likely veto | 22.4% | 14.3% |
| Bans and picks right as sets | 2.9% | 0.95% |
| Exact sequence of 7 | 3.3% | 0.02% |

Reading it: **the probability heatmap is more reliable than "the" most likely veto**. A modal
veto at 3% is not a bug: there are 5040 possible vetos. Opening bans (permaban) are the most
predictable part; the decider is the weakest.

Limits:
- **BO3 only.** BO5 has a different veto order and is not modelled.
- **Frozen snapshot** at `snapshot_date` (in `veto_meta`). With a 45-day decay it has to be
  re-exported whenever data is loaded.
- Teams without BO3 history use `__prior__` (average behaviour). Show `n_series`.
- Region does not enter the model (it cancels out), so it does not need filtering.

## 3. Snapshot schema (Supabase)

```sql
create table veto_team_map (
  team text not null, map text not null,
  ban_rate float8, pick_rate float8, fb_rate float8, winrate float8, played float8,
  rd_mean float8, is_permaban float8, wr_vs_own float8, wr_vs_expected float8,
  n_series int,
  primary key (team, map)
);
create table veto_map (
  map text primary key,
  ban_rate float8, pick_rate float8, ban_rate_60d float8, pick_rate_60d float8, series_in_pool float8
);
create table veto_coef (
  feature text primary key, mu float8, sg float8, b_pick float8, b_ban float8, b_ban2 float8
);
create table veto_meta (key text primary key, value text);
```

**RLS: without a policy, reads return 0 rows and no error.** Tables created from the dashboard
have RLS enabled. With the `anon` key and no policy, Supabase silently returns nothing; in the
app the symptom is `snapshot is missing the __prior__ rows` ("No veto model data"). Create the
read policy (idempotent):

```sql
drop policy if exists "anon read" on veto_team_map;
drop policy if exists "anon read" on veto_map;
drop policy if exists "anon read" on veto_coef;
drop policy if exists "anon read" on veto_meta;

create policy "anon read" on veto_team_map for select to anon using (true);
create policy "anon read" on veto_map      for select to anon using (true);
create policy "anon read" on veto_coef     for select to anon using (true);
create policy "anon read" on veto_meta     for select to anon using (true);
```

`float8` plus PostgREST output preserve the exact doubles from the CSV, so parity holds after
uploading.

**Re-exporting replaces, it does not add.** `scripts/upload.mjs` upserts: if a team disappears
from the snapshot, its old row stays. Truncate the four tables before uploading a new snapshot.

### 3.1 Migration from the first (Spanish) snapshot

The repo was translated to English on 2026-09-17 and four snapshot columns were renamed.
Feature names in `veto_coef` changed accordingly, but those are rows and are replaced by the
normal upload. Run once in rviewer's Supabase:

```sql
alter table veto_team_map rename column es_permaban    to is_permaban;
alter table veto_team_map rename column wr_vs_propio   to wr_vs_own;
alter table veto_team_map rename column wr_vs_esperado to wr_vs_expected;
alter table veto_map      rename column series_en_pool to series_in_pool;
```

Then, in the same go: copy the new `vetoPredict.ts` and `parity.test.ts` (steps 5.5), copy
`export/*` and upload (step 5.3), and run the parity test (step 5.4). The reference file was
also renamed: `veto_referencia.json` → `veto_reference.json` (delete the old one from `data/`).
The old engine reads the old column names, so the new engine and the new data must go live
together.

## 4. Engine API (`lib/vetoPredict.ts`)

- `buildSnapshot(teamMapRows, mapRows, coefRows, metaRows)` → `VetoSnapshot` (accepts numbers
  or strings).
- `vetoDistribution(snap, teamA, teamB, pool, locked = [], topN = 10)` → `mostLikely`,
  `sequences` (top N), `marginals[map][slot]`, `playedSets`, `categories`, `nSeries`.
  `teamA` is **the team that starts the veto**. Slots: `banA1, banB1, pickA, pickB, banA2,
  banB2, decider`.
- `stepProbabilities(snap, teamA, teamB, pool, taken)` → probabilities for the next step.
- `SLOT_ACTOR[slot]` → `'A' | 'B' | null` (decider), derived from the engine's veto order.
- `snap.testMetrics` → `since`, `nSeries`, and `{ model, chance }` for `top1Step`, `played`,
  `decider`, `categories`, `sequence`. `null` for snapshots without metrics.
- `knownTeam(snap, team)`, `snap.defaultPool`, `snap.snapshotDate`.

`vetoDistribution` throws on pools that are not 7 distinct maps, invalid locked maps and maps
missing from the snapshot; a UI that only offers snapshot maps never hits those.

The rviewer data layer (`lib/data/vetoModel.ts`, `getVetoModelRows`) returns **plain rows**
(serialisable for `unstable_cache` and for client props); the `VetoSnapshot` with its `Map`s is
built on the client with `useMemo`. Cache caveat: `versioned` invalidates when the latest match
date in `draft` changes, so a snapshot uploaded without new `draft` data can stay cached for up
to 24 h (or until the `vct-data` tag is revalidated).

In rviewer, `VetoPredictorSection.tsx` still holds hand-copied `ACCURACY` and `SLOT_ACTOR`
constants. They can now be replaced by `snap.testMetrics` and the exported `SLOT_ACTOR`, so a
retrain needs no UI edits.

## 5. Updating the model

1. **This repo:** run `map_veto_lightgbm.ipynb` end to end (~16 min: section 9 walks the 272
   test series for the metrics) → regenerates `export/`.
2. **This repo:** `node --experimental-strip-types rviewer_port/parity.test.ts` → `PARITY OK`.
3. **rviewer:** copy the veto files of `export/` (`veto_team_map.csv`, `veto_map.csv`,
   `veto_coef.csv`, `veto_meta.csv`, `veto_reference.json`) to `data/`. Not
   `veto_played_test.csv`: it only feeds the result notebook. The `result_*` files belong to the
   result model, see `RESULT_REPORT.md`. Truncate the tables
   (`truncate veto_team_map, veto_map, veto_coef, veto_meta;`) and run `node scripts/upload.mjs`
   (it currently only has the four `veto_*` entries enabled).
4. **rviewer:** `node --experimental-strip-types scripts/veto-parity.test.ts data` → `PARITY OK`.
5. **If `rviewer_port/vetoPredict.ts` changed:** copy it to `rviewer/lib/vetoPredict.ts` (and
   `parity.test.ts` to `scripts/veto-parity.test.ts`, with the import `../lib/vetoPredict.ts`;
   it stays excluded in `tsconfig.json`). If features changed in Python without touching the
   TS, step 2 fails.
6. **In-app check:** G2 (A) vs NRG (B) with the default pool shows the same most likely veto
   and probability as the `top_0` line printed by the parity test; locking the first two maps
   of the default pool matches `locked_2`.
